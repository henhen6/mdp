# 微信、QQ、钉钉登录与个人账号绑定设计

## 1. 背景与目标

MDP 当前支持用户名密码、手机短信、邮箱及微信小程序登录，用户表已有微信和钉钉 OpenID 字段，但网页端尚无完整的第三方登录与账号绑定能力。前端 `mdp-vben` 已有部分第三方登录图标和钉钉二维码雏形，但未形成安全、完整的认证闭环。

本期实现以下能力：

1. 工作台登录页接入微信网站应用、QQ、钉钉官方授权登录。
2. 已绑定用户授权后直接登录原 MDP 账号。
3. 未绑定用户授权后明确选择“绑定已有账号”或“创建新账号”，不静默注册。
4. 工作台个人中心支持查看、绑定和解绑第三方账号。
5. 用户误注册新账号后，可在验证双方身份的前提下，将第三方登录方式转移到已有账号，但不合并业务数据。
6. 绑定、解绑和跨账号转移均具备二次验证、票据防重放及最后登录方式保护。

## 2. 已确认的产品决策

| 决策点 | 结论 |
|---|---|
| 目标前端 | `/Users/tangyh/gitee/mdp-vben` 的 `web-workbench` |
| 首次第三方授权 | 展示“绑定已有账号 / 创建新账号”二选一 |
| 新账号注册门槛 | 确认协议后直接创建，不强制手机号或邮箱 |
| 误注册补救 | 安全转移第三方绑定，不合并账号和业务数据 |
| 授权交互 | 整页跳转第三方官方授权页，不做内嵌二维码 |
| 身份存储 | 新增独立第三方身份表，不继续扩展用户表 OpenID 字段 |
| 现有小程序 | 保留现有字段和登录逻辑，本期不迁移 |
| 敏感操作 | 绑定、解绑、转移都需要二次验证 |
| 解绑保护 | 不得移除用户最后一种可用登录方式 |

## 3. 范围边界

### 3.1 本期范围

- 微信网站应用（`WECHAT_OPEN`）、QQ（`QQ`）、钉钉（`DINGTALK`）。
- 工作台统一登录页及 OAuth 回调页。
- 工作台个人中心“安全设置”中的第三方账号卡片。
- 使用 JustAuth 1.16.7 完成第三方协议适配。
- 复用 MDP 现有账号校验、注册初始化、Sa-Token 会话和登录日志能力。
- MySQL 数据库脚本、后端行为测试、前端组件测试和构建验证。

### 3.2 非本期范围

- 微信小程序、公众号与网站应用 OpenID 的统一迁移。
- GitHub、Google 及其他第三方平台。
- 内嵌微信或钉钉二维码脚本。
- 同一 MDP 用户绑定多个同平台账号。
- 自动合并两个 MDP 用户的组织、角色、消息、资料或业务数据。
- 根据第三方返回的手机号或邮箱自动认领 MDP 账号。
- 保存第三方访问令牌，或调用与登录无关的第三方业务接口。
- 第三方应用参数的管理后台配置页面。

## 4. 现状与改造原则

### 4.1 可复用能力

- `AuthServiceImpl.login()` 已包含登录策略选择、账号校验、Sa-Token 登录及登录事件发布。
- `LoginStrategy` 已隔离用户名、手机和邮箱等认证方式。
- `UserFacade` 及控制台用户服务已包含默认组织、默认角色、人员编号等注册初始化逻辑。
- `ProfileController` 已承担个人资料和安全设置接口。
- 前端 `authStore.authLogin()` 已包含令牌保存、用户信息加载及登录跳转。
- 父工程已管理 JustAuth 依赖，无需引入另一套 OAuth 客户端。

### 4.2 改造约束

- 不改变现有 `/anyUser/auth/login` 的接口契约和认证行为。
- 不修改现有微信小程序登录流程及 `mdc_user.wx_openid`、`mdc_user.dd_openid` 的含义。
- 不复制一套第三方专用 token 签发逻辑。
- 不把第三方授权码、OpenID、访问令牌或密钥作为前端长期状态。
- 不通过“先查询、后插入”单独保证绑定唯一性，必须由数据库唯一索引兜底。

## 5. 总体架构

```text
工作台登录页 / 个人中心
          │
          ▼
SocialAuthController / ProfileSocialController
          │  仅负责参数接收和返回结果
          ▼
SocialAuthService / SocialAccountService
          │
          ├─ SocialProvider 策略
          │    └─ JustAuth：生成授权地址、code 换第三方身份
          │
          ├─ SocialTicketService
          │    └─ state、pendingTicket、reauthTicket 及一次性消费标记
          │
          ├─ AccountAuthenticator
          │    └─ 复用 LoginStrategy，校验已有 MDP 账号
          │
          ├─ LoginSessionService
          │    └─ 复用 Sa-Token、TokenSession、LoginVo 和登录事件
          │
          ├─ UserFacade
          │    └─ 注册用户并在本地事务中写入初始绑定
          │
          └─ UserSocialAuthService
               └─ 查询、绑定、解绑和转移第三方身份
```

### 5.1 针对性抽取

从 `AuthServiceImpl` 抽取两个职责明确的组件：

1. `AccountAuthenticator`：执行参数校验、用户查询、密码或验证码校验、用户状态检查，返回已验证用户，但不创建会话。
2. `LoginSessionService`：根据已验证用户创建 Sa-Token 会话、填充 TokenSession、构造 `LoginVo` 并发布登录事件。

普通登录、第三方绑定已有账号、个人中心二次验证复用第一个组件；普通登录和第三方登录复用第二个组件。此次抽取只服务于认证复用，不顺带调整其他业务。

## 6. 数据设计

### 6.1 新增表 `mdc_user_social_auth`

| 字段 | 类型建议 | 必填 | 说明 |
|---|---|---|---|
| `id` | BIGINT | 是 | 雪花 ID |
| `user_id` | BIGINT | 是 | MDP 用户 ID |
| `provider` | VARCHAR(32) | 是 | `WECHAT_OPEN`、`QQ`、`DINGTALK` |
| `client_id` | VARCHAR(128) | 是 | 第三方应用标识，用于隔离不同应用 OpenID |
| `open_id` | VARCHAR(128) | 是 | 第三方应用内用户标识 |
| `union_id` | VARCHAR(128) | 否 | 同主体跨应用标识，本期不作为自动认账依据 |
| `nickname` | VARCHAR(255) | 否 | 个人中心展示昵称 |
| `bound_at` | DATETIME | 是 | 最近绑定时间 |
| `created_at` | DATETIME | 是 | 创建时间 |
| `created_by` | BIGINT | 否 | 创建人 |
| `updated_at` | DATETIME | 否 | 更新时间 |
| `updated_by` | BIGINT | 否 | 更新人 |
| `deleted_by` | BIGINT | 否 | 删除人 |
| `deleted_at` | BIGINT | 是 | 逻辑删除标志，默认 0 |

### 6.2 唯一约束

有效数据需要满足：

```text
唯一约束 1：(provider, client_id, open_id, deleted_at)
唯一约束 2：(user_id, provider, deleted_at)
```

含义：

- 一个第三方应用身份只能属于一个有效 MDP 用户。
- 一个 MDP 用户最多绑定一个同平台网站登录身份。
- 逻辑删除的历史绑定不阻止重新绑定。
- 并发注册、绑定和转移最终均由数据库约束兜底。

### 6.3 数据安全

- 不保存第三方 `access_token`、`refresh_token` 或原始用户响应。
- 列表接口不返回 `open_id`、`union_id` 和 `client_id`。
- 昵称只用于展示，不自动覆盖 MDP 用户姓名。
- 旧用户表字段保留，不做数据回填，避免把小程序 OpenID 错当成微信网站应用 OpenID。

## 7. 核心业务流程

### 7.1 获取授权地址

1. 前端从 `/anyUser/social/providers` 获取已启用平台，只渲染可用入口。
2. 用户点击平台图标。
3. 后端生成高熵随机 `state`，保存平台、动作和过期时间；个人中心场景还保存当前用户 ID 和操作上下文。
4. 后端通过对应 `SocialProvider` 生成官方授权地址。
5. 浏览器整页跳转官方页面。微信、钉钉用户扫码确认，QQ 用户按官方页面完成授权。
6. 前端不接受任意第三方回调地址，也不把密钥注入页面。

### 7.2 已绑定身份直接登录

```text
第三方回调 code + state
          │
          ▼
校验 state 有效、未使用、平台匹配且 action = LOGIN
          │
          ▼
JustAuth 换取标准 SocialIdentity
          │
          ▼
按 provider + clientId + openId 查询有效绑定
          │
          ▼
加载 MDP 用户并检查状态
          │
          ▼
LoginSessionService 签发登录结果
```

- 回调路由为 `/auth/social/callback/:provider`。
- 后端同时校验路径平台与 state 中平台，防止混用。
- 第三方登录日志使用独立认证类型，不能伪装成用户名密码登录。
- 用户被禁用或删除时拒绝登录，不自动新建账号。

### 7.3 未绑定身份进入待选择状态

未查询到绑定时：

1. 后端创建有效期 10 分钟的 `pendingTicket`。
2. Redis 保存已经验证的 `SocialIdentity`，前端仅获得票据、平台和昵称。
3. 登录结果使用明确状态，例如 `SUCCESS` 或 `PENDING`，不以系统异常表示正常待选择流程。
4. 前端在同一回调页面展示两个选择，不把 `pendingTicket` 放入 URL。

### 7.4 绑定已有账号

输入：

- `pendingTicket`；
- 现有用户名密码、手机验证码或邮箱凭据；
- 设备信息。

处理顺序：

1. 校验待选择票据有效且未完成过其他操作。
2. 使用 `AccountAuthenticator` 验证目标 MDP 用户。
3. 检查目标用户状态及其是否已绑定同平台。
4. 再次检查第三方身份仍未被其他用户绑定。
5. 原子消费票据并建立绑定。
6. 通过 `LoginSessionService` 登录目标用户。

约束：

- 凭据失败不立即消耗票据，但累计失败达到 5 次后使票据失效。
- 目标账号已有同平台绑定时，提示先解绑，不自动覆盖。
- 第三方身份已被其他用户绑定时，要求重新扫码并走合法转移流程。
- 不使用第三方手机号或邮箱跳过 MDP 账号验证。

### 7.5 创建新账号

输入：

- `pendingTicket`；
- 显示姓名，默认取第三方昵称；
- 注册身份 `nature`，沿用现有注册身份校验；
- 用户协议确认；
- 设备信息。

处理规则：

1. 不强制补充手机号或邮箱。
2. 系统使用随机值生成唯一用户名，不用 OpenID 拼接用户名。
3. 生成随机高强度初始密码，不使用统一默认密码，也不向日志输出。
4. 复用现有默认组织、默认角色、人员编号及用户事件初始化逻辑。
5. 记录第三方注册来源，但不以第三方昵称覆盖后续用户资料。
6. 控制台用户服务在同一本地事务中创建用户、组织角色关系和第三方绑定，避免微服务场景拆成两个不具备原子性的远程写请求。
7. 成功后消费票据并自动登录；任何一步失败均回滚用户及绑定数据。

## 8. 个人中心账号管理

### 8.1 展示内容

在安全设置页新增“第三方账号”卡片，每个平台展示：

- 平台图标和名称；
- 是否绑定；
- 已绑定昵称和绑定时间；
- 未绑定时的“绑定”按钮；
- 已绑定时的“解绑”和“转移到已有账号”按钮。

未配置或未启用的平台不展示操作入口。页面状态完全来自 `/profile/social/list`。

### 8.2 二次验证票据

绑定、解绑和转移前均需获得 `reauthTicket`：

- 有效期 5 分钟；
- 绑定当前 MDP 用户；
- 绑定操作类型：`BIND`、`UNBIND` 或 `TRANSFER`；
- 绑定目标平台；
- 成功后一次性消费，不能跨用户、跨平台或跨动作使用。

支持以下验证方式：

1. 当前 MDP 用户名和密码；
2. 当前手机号和短信验证码；
3. 当前邮箱和邮箱验证码；
4. 当前账号已绑定的第三方身份重新授权。

账号凭据验证成功后，返回用户 ID 必须与当前登录用户一致，否则不能签发票据。

第三方重新授权时，回调得到的身份必须与当前用户所选平台的既有绑定完全一致。仅证明“扫码者拥有某个第三方账号”不足以通过当前 MDP 用户验证。

### 8.3 绑定

```text
当前账号二次验证
       │
       ▼
获得 action = BIND 的 reauthTicket
       │
       ▼
生成目标平台授权地址并跳转
       │
       ▼
回调校验当前会话、state、reauthTicket 和第三方身份
       │
       ▼
写入绑定并消费票据
```

- state 必须绑定发起操作的用户，回调时再次核对当前会话。
- 当前用户已有同平台绑定时，不自动替换，需先解绑。
- 第三方身份属于其他用户时，不自动抢占。
- 重复提交由一次性票据和唯一索引共同防护。

### 8.4 解绑

解绑前展示影响并验证 `reauthTicket`，然后检查操作后的剩余登录方式：

| 二次验证方式 | 可保留的登录能力 |
|---|---|
| 用户名密码 | 密码登录 |
| 手机验证码 | 手机短信登录 |
| 邮箱验证码 | 邮箱找回密码 |
| 第三方重新授权 | 解绑后仍存在至少一个其他有效第三方绑定 |

如果没有剩余可用登录方式，拒绝解绑并提示先补充联系方式或绑定其他平台。不能仅依据用户表中存在随机初始密码，就认定用户仍可通过密码登录。

解绑使用逻辑删除并记录审计信息。

### 8.5 误注册后的跨账号转移

场景：第三方身份已绑定误注册账号 A，用户实际希望使用已有账号 B。

处理步骤：

1. 当前会话登录 A，取得 `action = TRANSFER` 的 `reauthTicket`。
2. 输入 B 的用户名密码、手机验证码或邮箱凭据。
3. 验证 A 当前仍持有该第三方绑定。
4. 验证 B 状态正常，且未绑定同平台身份。
5. 原子消费票据，在一个数据库事务内将绑定关系从 A 改为 B，并更新绑定时间与审计字段。
6. 退出 A 的当前会话，使用 `LoginSessionService` 签发 B 的登录结果。

页面必须明确提示：

> 仅转移第三方登录方式；A 中的组织、角色、消息、资料和其他业务数据不会迁移。

其他约束：

- B 的验证仅接受 MDP 账号凭据，不能用当前待转移的第三方身份代替。
- A 不删除、不停用，B 的原有资料不被 A 覆盖。
- 转移是用户明确选择的账号切换，不适用“A 必须保留登录方式”的解绑限制。
- 记录 A、B、平台和操作时间，便于审计。

## 9. 接口设计

### 9.1 登录页公开接口

| 方法与路径 | 说明 | 主要返回 |
|---|---|---|
| `GET /anyUser/social/providers` | 获取已启用平台 | 平台编码和显示名称 |
| `GET /anyUser/social/{provider}/loginUrl` | 创建登录 state | 官方授权地址 |
| `POST /anyUser/social/login` | 处理登录回调 | `SUCCESS + LoginVo` 或 `PENDING + pendingTicket` |
| `POST /anyUser/social/bindExisting` | 绑定已有账号 | `LoginVo` |
| `POST /anyUser/social/register` | 创建并绑定新账号 | `LoginVo` |

所有接口遵循项目 `R<T>` 返回格式。分页规范不涉及本功能。

### 9.2 个人中心接口

| 方法与路径 | 说明 |
|---|---|
| `GET /profile/social/list` | 查询当前用户绑定列表 |
| `POST /profile/social/reauth` | 通过 MDP 账号凭据获取二次验证票据 |
| `POST /profile/social/{provider}/reauthUrl` | 生成第三方重新授权地址 |
| `POST /profile/social/reauthByCallback` | 处理第三方重新授权并返回票据 |
| `POST /profile/social/{provider}/bindUrl` | 校验绑定票据并生成目标平台授权地址 |
| `POST /profile/social/bind` | 完成绑定 |
| `POST /profile/social/unbind` | 完成解绑和最后登录方式检查 |
| `POST /profile/social/transfer` | 验证双方账号并转移绑定 |

### 9.3 登录结果模型

第三方登录回调使用显式结果状态：

```text
SUCCESS：返回 LoginVo，由前端统一完成登录。
PENDING：返回 pendingTicket、provider、nickname，由用户选择后续操作。
```

`pendingTicket`、`reauthTicket` 不作为查询参数放入浏览器地址。前端完成回调读取后立即清除地址栏中的 `code` 和 `state`。

## 10. 配置设计

三个平台分别配置：

```text
enabled
client-id
client-secret
redirect-uri
```

配置要求：

- 默认全部关闭，未配置完整时不对外启用。
- 密钥只通过环境变量或配置中心注入，不设置真实默认值。
- `redirect-uri` 指向工作台统一回调页，并与第三方平台后台白名单完全一致。
- 生产回调地址必须使用 HTTPS。
- 第三方协议端点由 JustAuth 维护，业务代码不硬编码。
- JustAuth 请求对象按请求创建，配置Bean不保存用户级授权状态。
- 前端公开接口只返回平台编码和显示名称，不下发密钥或完整应用配置。

## 11. Redis 与并发设计

| 数据 | 有效期 | 主要内容 |
|---|---:|---|
| OAuth state | 10 分钟 | 平台、动作、用户上下文、操作上下文 |
| pendingTicket | 10 分钟 | 已验证第三方身份、失败次数 |
| reauthTicket | 5 分钟 | 用户、动作、平台 |
| 一次性消费标记 | 与原票据一致 | 防止集群并发重放 |

项目现有 `CacheOps` 没有原子 `getAndDelete`，因此不采用“先 get 再 del”的非原子方案。一次性消费通过 `CacheOps.setIfAbsent` 写入独立消费标记实现：

- 只有一个并发请求能成功创建标记；
- 未获得标记的请求按重复回调处理；
- 票据在最终业务写入前消费，若随后发生数据库冲突，用户需重新发起操作；
- 普通密码错误不消费 `pendingTicket`，但会增加失败次数；
- 所有缓存键使用项目 `CacheKeyBuilder` 规范，不散落字符串拼接和原生 Redis 调用。

## 12. 前端设计

### 12.1 登录页

- 在工作台登录页通过第三方登录插槽接入本期专用组件。
- 仅展示后端返回的已启用平台，不展示 GitHub、Google 等未实现入口。
- 跳转前保存必要的内部登录上下文，用于成功后回到原目标页；回调地址本身不接受任意外部跳转。
- 复用并抽取 `authStore` 的登录完成逻辑，统一保存 token、加载用户信息和跳转。

### 12.2 回调页

回调页包含以下状态：

```text
处理中
  ├─ 登录成功：完成登录并跳转
  ├─ 待选择：绑定已有账号 / 创建新账号
  └─ 失败：显示具体原因，提供返回登录或重新授权
```

- 待选择页面不依赖 URL 保存票据，刷新导致票据上下文丢失时引导重新授权。
- 绑定已有账号复用现有用户名、手机、邮箱表单和验证码发送能力。
- 创建新账号展示第三方昵称、显示姓名、注册身份和协议确认。

### 12.3 安全设置页

新增第三方账号卡片及以下弹窗：

- 当前账号二次验证；
- 解绑影响确认；
- 转移账号凭据及“不迁移业务数据”确认。

操作成功后重新拉取绑定列表；失败时保留用户已填写的不敏感字段，不回显密码、验证码或票据。

## 13. 异常处理与日志

- 业务校验遵循 fail fast，使用具体 `BizException` 消息。
- state 不存在、过期、平台不符、动作不符或已消费时，返回“授权状态已失效，请重新发起”。
- 外部平台未启用或配置不完整时，返回“该平台暂未开放登录”。
- 第三方身份冲突时，明确提示已绑定其他用户，不泄露对方账号资料。
- 唯一索引冲突转换为可理解的业务提示，并记录必要上下文。
- 第三方调用异常记录平台及异常堆栈，不吞掉异常，不直接返回第三方原始报文。
- 日志不得记录 client-secret、授权码、访问令牌、OpenID、UnionID、密码、短信或邮箱验证码及完整回调地址。
- 认证失败不泄露“用户不存在”和“密码错误”的不必要差异，避免账号枚举。

## 14. 测试设计

### 14.1 后端行为测试

先编写 JUnit 5 测试，再实现功能，重点覆盖：

1. state 过期、重放、平台不匹配、动作不匹配。
2. 已绑定用户登录成功，以及禁用、删除用户登录失败。
3. 未绑定身份返回待选择结果且不创建用户。
4. 绑定已有账号成功、凭据错误、失败次数限制、目标平台冲突。
5. 新用户注册成功，以及用户或绑定任一步失败时整体回滚。
6. 注册时不强制手机或邮箱、不使用统一默认密码。
7. 二次验证票据跨用户、跨平台、跨动作及重放使用被拒绝。
8. 第三方重新授权身份与当前用户既有绑定不一致时被拒绝。
9. 绑定冲突和并发情况下数据库唯一约束生效。
10. 解绑最后一种登录方式被阻止；存在可用替代方式时成功。
11. 转移前双方验证、目标冲突、绑定原子转移及业务数据不变。
12. 普通用户名、手机、邮箱登录行为回归。
13. 日志和返回结果不包含密钥、令牌或 OpenID。

第三方 HTTP 调用在自动化测试中统一模拟，不依赖真实平台网络。

### 14.2 前端测试

- 回调成功、待选择和失败分支；
- 绑定已有账号与创建新账号提交；
- 登录成功统一保存令牌和加载用户；

### 14.3 真实平台验收

真实扫码需要有效的微信开放平台、QQ 互联和钉钉应用凭证，并配置回调白名单。每个平台至少验收：

1. 已绑定账号登录；
2. 未绑定后绑定已有账号；
3. 未绑定后创建新账号；
4. 个人中心绑定和解绑；
5. 最后登录方式保护；
6. 误注册账号转移到已有账号；
7. 回调刷新、重复提交和过期票据；
8. 禁用用户及第三方取消授权。

没有真实凭证时，只能声明模拟测试和构建验证结果，不能声称真实第三方链路已验收。

## 15. 验收标准

1. 三个平台能够根据配置独立启用，未启用平台不出现在登录页。
2. 已绑定第三方身份始终登录同一个 MDP 用户。
3. 未绑定授权不会直接产生用户，只有明确选择“创建新账号”后才注册。
4. 绑定已有账号必须通过 MDP 凭据验证，不依赖第三方手机号或邮箱自动认账。
5. 新账号具备现有注册流程要求的默认组织、角色和人员编号。
6. 个人中心可以查询、绑定和解绑，并且所有敏感操作均通过二次验证。
7. 最后一种可用登录方式不能被解绑。
8. 误注册后可将第三方身份转移到已有账号，且不改变两个账号的业务数据。
9. state、待选择票据和二次验证票据具备有效期、用途隔离和防重放能力。
10. 现有登录接口和微信小程序逻辑保持兼容。
11. 数据库、后端、前端及日志中不出现不应暴露的第三方密钥或令牌。

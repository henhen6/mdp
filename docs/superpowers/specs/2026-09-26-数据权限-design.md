# 数据权限设计

> 本文档由头脑风暴确认后成文（2026-09-26），是数据权限功能的最终需求基线。
> 与《用户角色组织权限体系设计.md》第 4 节"数据权限"段冲突时，以本文档为准
> （原基线是"角色全局一档"，本文档演进为"角色 × 菜单粒度"）。

## 0. 设计目标

实现灵活的、按菜单粒度配置与授权的数据权限：

1. **开发期**：程序员在菜单涉及的查询接口上，通过注解提前埋点。
2. **配置期**：在菜单管理界面配置哪些菜单启用数据权限控制。
3. **授权期**：在角色管理界面按菜单粒度选档——角色 A 在菜单 1 查看全部数据、
   菜单 2 查看本部门数据、菜单 3 查看本单位数据。

## 1. 决策汇总（头脑风暴确认）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 过滤维度 | 组织维度五档 + 自定义实现（SPI） |
| 2 | 埋点与菜单的关联 | 注解声明**菜单 code**（不写查询点编码，无绑定表） |
| 3 | 未授权的默认行为 | 菜单已启用数据权限但角色未授权 → **无数据**（注入永假条件 `id IS NULL`；不用 `1=0`，会被 Druid WallFilter 永假条件规则拦截） |
| 4 | 多角色合并 | 并集，按优先级取最高档 |
| 5 | 执行机制 | 注解 + AOP + **MyBatis Interceptor（Executor 层）+ JSqlParser 改写 SQL**，全覆盖 BaseMapper 方法 / QueryWrapper / XML 自定义 SQL / Db 工具 |
| 6 | 权限集合 | 控制数据权限的**菜单 + 档位**（委派链：运营者→权限集合→普通角色） |
| 7 | 存量处置 | **全部推翻重写**：删除旧 datapermission 包、`mdc_role.data_scope` 系列字段、`mdc_resource_data_perm` 表 |
| 8 | 档位优先级 | **全部数据 > 自定义 > 本公司及以下 > 本部门及以下 > 本部门 > 仅本人** |

## 2. 三阶段数据流

```
① 开发期（程序员埋点）
   查询方法上加注解：
   @DataScope(code = "organization:user",      // 菜单 code（稳定业务键）
              orgColumn = "dept_id",           // 组织列
              userColumn = "created_by",       // 用户列
              tableAliases = {"u"})            // 过滤目标表别名，支持多个，可选
        ▼
② 配置期（菜单管理界面）
   菜单表单增加"数据权限"开关（mdc_resource_menu.data_scope_state）
   启用即视为该菜单纳入数据权限控制
        ▼
③ 授权期（角色管理界面）
   角色 → 数据权限 Tab → 已启用数据权限的菜单树 → 逐菜单选档
   （五档 或 自定义实现；可选项 ⊆ 本组织性质权限集合的授权集）
        ▼
   运行期：注解触发 → 按菜单 code 找菜单 → 查（用户角色 × 菜单）授权
          → 并集取最高优先级档 → 拼 WHERE
```

**生效链**：`菜单code → 菜单 → (角色 × 菜单)授权 → 档位 → WHERE 条件`

## 4. 注解设计

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
    /** 菜单 code（全局唯一业务键，跨环境稳定） */
    String code();
    /** 组织列名（组织类档位的过滤列；不声明则该查询不支持组织类档位） */
    String orgColumn() default "";
    /** 用户列名（仅本人档的过滤列） */
    String userColumn() default "created_by";
    /**
     * 过滤目标表别名，支持 1..n 个；仅改写声明别名涉及的表。
     * 单表查询可省略（省略时仅允许单表语句，多表语句 fail fast）
     */
    String[] tableAliases() default {};
}
```

- 标注在 Mapper 或 Service 的**查询方法**上；只对 SELECT 生效。
- 档位基准：`CurrentDeptId` / `CurrentCompanyId` / `UserId` 一律取登录上下文
  （ContextUtil），多组织用户切换组织后自动按新上下文过滤。
- **"本部门"档位的部门基准回落规则**：用户直接挂公司节点时登录上下文的
  部门 id 为空，此时"本部门"按其组织单元（公司）计算——即部门基准 =
  `deptId ?? companyId`，统一由 `ContextUtil.getCurrentDeptOrCompanyId()`
  提供（数据权限装配与业务写入侧都走此方法，保证读写一致）。
  语义：本部门 = 我的组织单元（是部门按部门、是公司按公司）；
  两者皆空（无组织用户）仍按无数据处理（fail-closed）。

## 5. 执行引擎（重写 datapermission 包）

### 5.0 拦截机制选型（2026-09-26 确认）

**为什么不用方言（Dialect）**：反编译 mybatis-flex-core 1.11.7 确认，方言挂钩点
（`forSelectByQuery`、`prepareAuth` 三个重载）只覆盖框架生成的 SQL
（QueryWrapper 查询、BaseMapper 按 ID 查询），**XML 自定义 SQL、`@Select`
注解 SQL 完全绕过方言**。而多表 join 的复杂查询恰恰最需要数据权限。

**选定方案**：MyBatis Interceptor 拦截 `Executor#query`，用 JSqlParser 解析并
改写 BoundSql，往目标表的 WHERE 注入数据范围条件。一个机制通吃所有查询路径：

| 查询路径 | 方言方案 | 本方案 |
|---|---|---|
| QueryWrapper 查询（selectListByQuery、paginate） | ✅ | ✅ |
| BaseMapper 预定义方法（selectOneById 等） | ⚠️ 需重写 prepareAuth 才覆盖 | ✅ |
| XML 自定义 SQL / @Select | ❌ | ✅ |
| Db 工具类（Db.selectListByQuery 等） | ✅ | ✅ |
| 分页 count 查询（同线程内自动过滤，保证总数正确） | ✅ | ✅ |

代价：引入 `com.github.jsqlparser:jsqlparser` 依赖（md-db-mybatis-flex 模块）；
SQL 解析失败按 fail fast 处理（埋点方法的 SQL 必须可解析，开发期即暴露）。

### 5.1 运行期判定流程

```
AOP 切面：带 @DataScope(code=C) 的方法进入 → 注解压入 ThreadLocal（保存外层旧值）
拦截器：Executor#query 逐语句判定
  ├─ ThreadLocal 无注解（非埋点查询）        → 放行
  ├─ 无登录上下文（worker/MQ/系统线程）       → 放行（系统内部调用不过滤）
  ├─ 菜单 C 不存在或 data_scope_state 未启用  → 放行（埋点≠启用，联调期不误伤）
  ├─ 目标表匹配（见 5.2）：本语句不涉及目标表 → 放行（辅助查询不受污染）
  ├─ 查当前用户所有启用角色对该菜单的授权
  │    ├─ 全部角色均未授权                  → 注入 id IS NULL（无数据）
  │    ├─ 任一角色授权=全部数据              → 放行
  │    ├─ 最高优先级档=自定义                → 执行 DataScopeCustomHandler
  │    │    （多个自定义并存 → 各 handler 条件 OR 合并）
  │    └─ 否则                              → 按最高优先级内置档生成条件，JSqlParser 注入 WHERE
  └─ 自定义档 Bean 不存在 / 组织类档位但注解未声明 orgColumn
                                           → fail fast 抛 ArgumentException
```

### 5.2 目标表匹配规则（防止误改辅助查询）

注解标在 Service 方法上时，方法内所有 SQL 都是候选语句（主列表、字典回显、
组织树等），必须精确识别"哪条语句该过滤"。支持单表与多表
（inner join / left join / right join）查询：

- **声明了 `tableAliases`（1..n 个）**：
  - 语句中出现任一声明别名（FROM 或任意 JOIN 子句）→ 对每个命中的声明别名
    注入条件（多个别名命中时条件以 AND 连接），列写作 `alias.orgColumn` /
    `alias.userColumn`。
  - 一个声明别名都没出现 → 该语句是辅助查询，跳过不改写。
- **未声明 `tableAliases`**：仅改写**单表语句**（FROM 只有一个表），条件写作
  裸列名；遇到多表语句 → **fail fast 抛异常**，提示开发者补充 `tableAliases`
  （不静默跳过，避免"以为过滤了其实没过滤"的越权隐患）。
- **注入位置**：条件以 AND 追加到语句的 WHERE 子句（无 WHERE 则创建）。
  即使过滤目标是 left/right join 的可空侧表，也注入 WHERE 而非 ON——
  数据权限的语义是"结果集行过滤"，可空侧不满足范围的行本就不该返回。
- 分页插件生成的 count 语句适用同一规则，保证分页总数与列表一致。

### 5.3 档位 → SQL 映射

| 档位 | WHERE 条件 |
|---|---|
| 全部数据（10） | 不加条件，直接放行 |
| 自定义（90） | 委托 `DataScopeCustomHandler.apply()` |
| 本公司及以下（20） | `orgColumn IN (SELECT id FROM mdc_org WHERE tree_path LIKE '/{companyId}/%')` |
| 本部门及以下（30） | 同上，根为 `{deptId}` |
| 本部门（40） | `orgColumn = currentDeptId` |
| 仅本人（50） | `userColumn = currentUserId` |

- 组织子树用 `mdc_org.tree_path` 前缀匹配，不用外键、不加递归。
- 多表查询用 `tableAlias` 限定过滤列归属。

### 5.4 多角色合并规则

优先级：**全部数据 > 自定义 > 本公司及以下 > 本部门及以下 > 本部门 > 仅本人**

- 取用户所有启用角色在该菜单上的授权档，按优先级取最高档生效（并集语义）。
- 最高档为自定义且有多个不同实现时，各 handler 的过滤条件以 OR 合并。
- 未授权的角色贡献空集、不影响其他角色；只有全部角色都未授权时才无数据。

### 5.5 实现要点

- **嵌套查询保护**：带注解方法内调用另一个带注解方法时，内层覆盖 ThreadLocal
  上下文，方法结束后**恢复外层旧值**（切面保存旧值，而非直接 remove），
  避免外层查询被内层编码污染。
- **引擎内部查询隔离（防自递归）**：拦截器调用 Provider（查菜单/查授权）与
  改写器调用自定义 handler 时，必须先用 `setAndGetPrevious(null)` 隔离上下文、
  结束后恢复——这些内部查询会再次经过拦截器，不隔离会无限自递归
  （StackOverflowError）。自定义 handler 实现里查库是安全的（隔离由引擎保证）。
- **解析性能**：JSqlParser 解析结果按 statementId 缓存（同语句只解析一次），
  授权数据按 `菜单code → 菜单`、`用户 → 授权集合` 走 CacheOps 缓存，
  角色授权/角色用户绑定变更时失效；过滤不产生额外 join，
  子查询走 `mdc_org` 索引。
- **注解位置**：推荐标在 **Service 查询方法**上（Spring AOP 天然生效，
  方法内主查询与辅助查询靠 5.2 目标表规则区分）；标在 Mapper 接口方法上
  亦可（Mapper 也是 Spring Bean，可被 AOP 代理），实现期验证后固化约定。
- **拦截器注册**：通过 MyBatis `Configuration#addInterceptor` 注册，
  拦截 `Executor#query(MappedStatement, Object, RowBounds, ResultHandler)`，
  在分页插件之前执行改写。
- **自定义 SPI**：

```java
public interface DataScopeCustomHandler {
    void apply(DataScope annotation, DataScopeCurrentUser currentUser, QueryWrapper queryWrapper);
}
```

`DataScopeCurrentUser` 为引擎内建的当前用户视图（userId、deptId、companyId、
生效授权集合），由方言层组装后传给 handler。
实现类注册为 Spring Bean，授权时在角色的 `data_scope_impl` 配置 Bean 名。

## 7. 边界与错误处理

| 场景 | 行为 |
|---|---|
| worker/MQ/系统线程（无登录上下文） | 放行，不过滤 |
| 埋点了但菜单未启用数据权限 | 放行 |
| 菜单已启用但角色未授权 | 注入 `id IS NULL`（永假条件，兼容 Druid 墙规则），无数据 |
| 组织类档位但注解未声明 orgColumn | 抛 `ArgumentException`（配置错误 fail fast） |
| 自定义档 Bean 不存在 | 抛 `ArgumentException`（配置错误 fail fast） |
| 多表语句但注解未声明 tableAliases | 抛 `ArgumentException`（不静默跳过，防"以为过滤了"） |
| 埋点方法的 SQL 无法被 JSqlParser 解析 | 抛异常（fail fast，开发期即暴露） |
| 多组织用户 | 以登录上下文当前部门/公司为准 |
| 用户直接挂公司节点（部门为空） | "本部门/本部门及以下"按其公司计算（deptId 回落 companyId）；无组织用户仍无数据 |
| 内置角色（运营管理员等） | 菜单启用数据权限时自动为"管理员角色+全部权限集合"授予"全部数据"，避免管理员体系被 1=0 挡住。**已确认取舍（2026-09-26）**：这意味着角色管理对新启用菜单默认可分配（六档全开），不强制"角色模板先配置一次"——若未来要收紧为默认关闭，需收窄联动范围并保留运营管理员权限集作为委派链自举起点 |

## 8. 权限集合控制

- 「角色管理」数据权限 Tab 的可分配（菜单 × 档位）选项 =
  操作人所在**组织性质的权限集合**角色的授权集（菜单不能超集、档位不能更高）。
- 与操作人自身拥有的权限无关，形成委派链：运营者 → 权限集合 → 普通角色。
- 权限集合自身的数据权限授权在「角色模板」页维护，复用同一授权组件。

## 9. 测试策略（TDD）

- **引擎纯单测**（不启 Spring，重写原 DataScopeTest/EffectiveRolesTest）：
  - 五档 + 自定义的 SQL 改写全覆盖（单表、inner/left/right join 多表语句）
  - 目标表匹配：多别名声明时逐别名注入；辅助查询（不含声明别名）不被改写；
    多表未声明别名 fail fast
  - 合并规则：优先级取档、多自定义 OR 合并、未授权注入永假条件、全部数据短路
  - 放行路径：无注解、无上下文、菜单未启用
  - 嵌套查询的外层恢复；分页 count 语句同步过滤
  - fail fast：缺 orgColumn、Bean 不存在、SQL 解析失败
  - XML 自定义 SQL 路径的拦截（不经过 QueryWrapper 的语句同样被改写）
- **服务层单测**：授权保存/更新（唯一约束、自定义档必须填 Bean 名）、
  权限集合范围过滤、菜单开关变更。

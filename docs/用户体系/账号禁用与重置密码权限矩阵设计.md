# 账号禁用 / 重置密码权限矩阵设计

> 本文档由头脑风暴确认后成文（2026-09-25），是「禁用/启用账号、重置密码」两个操作的最终需求基线。
> 本文档取代《用户角色组织权限体系设计.md》第 5 节中关于运营者"不可被禁用、除本人外不可被重置密码"的旧规则；
> 删除用户、解绑角色、角色保护、内置组织保护等其余硬保护规则不变，仍由 `SystemProtectService` 承担。

## 1. 设计目标

ops_admin 是系统最高账号，必须内置在系统中；若其无法正常使用、登录或管理其他账号，则系统会出现问题。
权限大小：

```
ops_admin > 运营者下的其他账号 > open_admin > 开发者下的其他账号
ops_admin > 运营者下的其他账号 > admin     > 总公司下的其他账号
```

open_admin 与 admin 权限内容不同，但属于平级。

## 2. 操作矩阵

作用于"别人"的账号时（操作人 ≠ 目标）：

| 操作人 \ 目标 | ops_admin | 其他运营者 | open_admin | admin | 开发者树下账号 | 总公司树下账号 |
|---|---|---|---|---|---|---|
| **ops_admin** | —（见通用规则） | ✅ 禁用/启用/重置密码 | ✅ | ✅ | ✅ | ✅ |
| **其他运营者** | ❌ | ❌（平级互不可管） | ✅ | ✅ | ✅ | ✅ |
| **open_admin** | ❌ | ❌ | —（见通用规则） | ❌ | ✅ | ❌ |
| **admin** | ❌ | ❌ | ❌ | —（见通用规则） | ❌ | ✅ |
| **其余账号** | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

通用规则（与身份无关，优先级最高）：

1. **任何人不能禁用自己的账号**（防自我锁死）。
2. **任何人可以重置自己的密码**（控制台重置密码入口；自助改密码仍走工作台）。
3. **任何账号不能禁用 ops_admin**；**除 ops_admin 本人外，任何账号不能重置 ops_admin 的密码**。
4. 启用 ops_admin 不受限制（ops_admin 本就无法被禁用，启用是无害恢复操作）。
5. 「启用」与「禁用」适用同一矩阵（管理范围包含禁用/启用两个方向）。

识别方式：

- **ops_admin / open_admin / admin 按内置用户 ID 识别**，新增 `BuiltInUserId` 常量接口
  （`md-common-pojo` 的 `top.mddata.common.constant` 包，仿 `BuiltInOrgId`）：
  `OPS_ADMIN=680083598598475778`、`OPEN_ADMIN=680083598598475779`、`ADMIN=680083598598475780`，
  与 `docs/mdp.sql` 内置数据一一对应，属于跨环境契约，禁止修改。
- **运营者按角色识别**：持有启用状态的「运营管理员」角色（`RoleCode.OPERATIONS_ADMIN`），
  与 `SystemProtectService` 现有判定口径一致。
- 注意：open_admin/admin 按 ID 识别意味着——若运营者日后创建第二个"开发者管理员"子账号，
  该子账号不属于 open_admin，按矩阵无权禁用/重置他人账号。

## 3. 架构：策略模式

```
UserServiceImpl
 ├─ updateBefore()   ── state 真实变化时 ─┐
 └─ resetPassword() ──────────────────────┤
                                          ▼
                              AccountOperationGuard（门面，统一入口）
                                          │ 1. 通用规则前置拦截（与身份无关）
                                          │ 2. 按操作人匹配策略（有序，取首个 supports=true）
                                          ▼
        ┌──────────────┬──────────────┬──────────────┬──────────────┐
   OpsAdmin      OperationsAdmin   OpenAdmin       HeadCompanyAdmin  （无匹配→拒绝）
   Strategy      Strategy          Strategy        Strategy
```

- 每个策略类只回答一个问题："我这类操作人，能否对这个目标执行该操作"，不能则 fail fast 抛 `ArgumentException`。
- 策略只依赖 Mapper（`UserRoleRelMapper`、`RoleMapper`、`UserOrgRelMapper`、`OrgMapper`），
  与 `SystemProtectServiceImpl` 同样的依赖方向，避免与业务 Service 形成循环依赖。
- 新增一类操作人 = 新增一个 Spring Bean 策略并排序，门面和调用方零改动。

## 4. 组件清单

均新增于 `console-service` 的 `top.mddata.console.service.organization.accountop` 包：

| 组件 | 职责 |
|---|---|
| `AccountOperation` 枚举 | `DISABLE` / `ENABLE` / `RESET_PASSWORD` |
| `TargetAccountProfile` | 目标账号画像：`isOperationsAdmin`、`inDeveloperTree`、`inHeadCompanyTree`；由门面一次性查询组装，策略内零查询 |
| `AccountOperationStrategy` 接口 | `boolean supports(Long operatorId)` + `void check(AccountOperation op, TargetAccountProfile target)` |
| `OpsAdminStrategy` | 操作人 = `BuiltInUserId.OPS_ADMIN`；放行一切（通用规则已排除自身与 ops_admin 目标） |
| `OperationsAdminStrategy` | 操作人持有启用状态 OPERATIONS_ADMIN 角色；目标是运营者 → 拒绝，其余 → 放行 |
| `OpenAdminStrategy` | 操作人 = `BuiltInUserId.OPEN_ADMIN`；目标在开发者平台树内 → 放行，否则拒绝 |
| `HeadCompanyAdminStrategy` | 操作人 = `BuiltInUserId.ADMIN`；目标在总公司树内 → 放行，否则拒绝 |
| `AccountOperationGuard` 接口 + Impl | 通用规则 + 策略调度；无策略命中 → 拒绝 |
| `BuiltInUserId` 常量接口 | `md-common-pojo` 的 `top.mddata.common.constant` 包，仿 `BuiltInOrgId` |

目标组织树归属判定：`mdc_user_org_rel` 内联 `mdc_org`，按 `tree_path like '/{rootId}/'` 匹配，
与 `OrgVisibilityService.appendUserVisibilityFilter` 同一套路（rootId 取 `BuiltInOrgId.DEVELOPER_PLATFORM` /
`BuiltInOrgId.HEAD_COMPANY`）。

## 5. 门面执行流程

按顺序执行，命中即返回/抛出：

1. **目标是自己**：`DISABLE` → 拒绝"不能禁用自己的账号"；`ENABLE` / `RESET_PASSWORD` → 直接放行。
2. **目标是 ops_admin**：`DISABLE` → 拒绝；`RESET_PASSWORD` → 拒绝（本人已在第 1 条放行）；`ENABLE` → 放行。
3. **策略调度**：按 `OpsAdmin → OperationsAdmin → OpenAdmin → HeadCompanyAdmin` 顺序取首个
   `supports(operatorId)=true` 的策略执行 `check`；**无策略命中 → 拒绝**（"其他账号不能禁用和重置密码"）。

## 6. 接入点改动（仅 2 处）

1. `UserServiceImpl.resetPassword`：
   `systemProtectService.checkUsersNotProtected(...)` → `accountOperationGuard.check(targetId, RESET_PASSWORD)`
   （操作人由门面内部 ContextUtil.getUserId() 获取，调用方无法伪造）。
2. `UserServiceImpl.updateBefore`：删除现有"禁用拦截运营者"逻辑，改为**检测 state 真实变化**
   （对比数据库现值：`true→false` 为 `DISABLE`，`false→true` 为 `ENABLE`，未变化不拦截），调用 guard。
   仅 state 变化触发矩阵校验，其余字段修改不受影响。

其余写入口（删除用户、解绑角色、角色保护、内置组织保护）保持现有 `SystemProtectService` 规则不动；
账号解锁（unlock）本次不改。

## 7. 错误处理

所有拒绝走 `ArgumentException`（fail fast），消息具体到操作与原因，例如：

- `禁用失败：ops_admin 是系统最高账号，禁止禁用`
- `禁用失败：不能禁用自己的账号`
- `重置密码失败：无权重置运营者账号的密码`
- `禁用失败：无权操作该账号`

## 10. 删除保护（2026-09-25 补充）

- 3 个内置账号（ops_admin、open_admin、admin，按 `BuiltInUserId` 内置用户 ID 识别）**任何人**都不能删除，
  包括 ops_admin 删除自己——内置账号必须永远存在，否则系统会出现问题。
- 识别方式选择用户 ID 而非用户名：用户名可通过用户编辑修改，按用户名判断会在改名后静默失效；
  ID 是雪花主键终身不变，且与 `BuiltInOrgId` 同一套契约模式。
- 非内置账号的删除不做权限矩阵，保持现有语义（菜单权限 + 运营者不可删的既有硬保护）。
- 实现：`AccountOperation.DELETE` 走 `AccountOperationGuard` 通用规则（最前置，不走策略）；
  `UserServiceImpl.removeByIds` 在 `checkUsersNotProtected` 之后逐 id 调用。

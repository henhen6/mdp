# 用户 / 角色 / 组织 / 权限体系设计

> 本文档由头脑风暴确认后成文（2026-09-24），是用户体系、角色体系、组织体系、权限体系的最终需求基线。
> 原始讨论稿见同目录《需求.md》，本文档与《需求.md》冲突时以本文档为准。

## 0. 设计目标

MDP 是基础开发底座，只关注基础数据维护，不涉及复杂业务逻辑。二次开发时可通过扩展组织性质来扩展身份（如教学系统的老师/学生、招采系统的采购主体/供应商等）。

## 1. 身份模型：角色即身份

系统内置三种用户身份：

| 身份 | 说明                                        | 可进入的端 |
|---|-------------------------------------------|---|
| 运营者 | 保障系统正常运转的人员，拥有系统最高权限，包括系统级数据配置、菜单配置、资源分配等 | 控制台、开发者中心、工作台 |
| 开发者管理员 | 系统层面管理全体开发者的管理人员（如审批应用申请），由运营者创建子账号，不开放注册 | 控制台、开发者中心、工作台 |
| 开发者 | 申请应用、对接应用的人员，任何人都能注册成为开发者                 | 开发者中心、工作台（不能进控制台） |
| 用户 | 使用 MDP 系统的普通用户，也可以有单独的业务管理员               | 工作台、控制台（部分） |

规则：

- **身份由角色决定**。删除 `mdc_user.user_type` 字段。
- 判定规则：用户绑定了组织性质为 `99-运营` 的管理员角色 → 运营者；绑定了性质为 `90-开发者` 的管理员角色 → 开发者管理员；绑定了性质为 `90-开发者` 的其他角色 → 开发者；其余 → 普通用户。
- 所有按 `userType` 过滤/统计的既有功能（用户管理查询、用户增长趋势统计等）一律改为按角色判定。
- 端的准入不加额外开关，由角色的应用权限天然保证（开发者角色不分控制台应用，自然进不去）。

## 2. 组织模型：三棵独立树

内置 3 个根公司，均不可删除、不可移动、不可修改组织性质：

```
├─ 总公司      （性质=1 总公司） ── 下设内置「默认部门」，普通用户注册落入该部门
├─ 开发者平台  （性质=90 开发者）── 开发者注册落入该公司；开发者管理员子账号也挂在该公司下
└─ 运营中心    （性质=99 运营）  ── 运营者账号在该公司下
```

规则：

- 组织管理页面：普通用户只能看到「总公司」及其子树，看不到「开发者平台」「运营中心」；开发者管理员只能看到「开发者平台」及其子树；运营者可见全部三棵树；开发者无组织管理入口。
- 运营者、开发者的公司与普通用户的公司物理隔离，不靠查询过滤模拟。
- 二次开发扩展新身份 = 新增组织性质 + 新增根公司，机制不变。
- **组织性质是 `mdc_org` 表的一个字段（`nature`），废弃独立的 `mdc_org_nature` 表**。MDP 是基础平台，不允许出现"一个组织多个性质"的场景——否则控制台、工作台都得做性质切换功能，复杂度不可接受。一个组织有且只有一个性质。
- 性质只在公司层级维护；部门继承其所属公司的性质（实现上取顶级公司的性质即可，部门行的字段冗余同步）。
- 内置性质：`1-总公司 90-开发者 99-运营`。
- 二次开发时，若子系统有一个公司拥有多个性质的场景，只需要在子系统中单独设计组织性质即可，不能与系统内置的3个组织性质混为一谈。（比如：招采系统中一个公司可以同时是供应商和代理机构）

## 3. 角色模型

`mdc_role` 保留字段：`code / name / roleCategory / orgNature / templateRole / state / remarks`。**删除 `roleType` 字段**（功能/桌面/数据角色的维度废弃，角色能力由绑定的资源决定）。

**`orgNature` 存性质编码（1/90/99），不存 org_id**。角色的分层是"组织性质级"的概念而非"公司级"：权限集合/管理员角色的唯一约束是 `(roleCategory, orgNature)`；内置角色（如「普通用户」）属于性质这个抽象，不隶属于某一行公司数据；性质编码是枚举常量、跨环境稳定，初始化脚本可直接引用。若子系统将来需要"每公司一套角色"，在子系统内单独扩展（如自建角色-公司关系表），不修改底座。

角色分类 `roleCategory`：

- `10-普通角色`：拥有组织下部分权限，由各管理员在「角色管理」维护。
- `20-管理员角色`：每个组织性质下最多 1 个，拥有该性质的最高权限。
- `30-权限集合`：每个组织性质下最多 1 个，用于控制该性质下「角色管理」能分配的权限范围。

内置角色清单：

| 角色 | 分类 | 组织性质 | 绑定对象 | 说明 |
|---|---|---|---|---|
| 运营管理员权限集 | 权限集合 | 99 运营 | — | 控制运营者在角色管理可分配的范围（=全量权限） |
| 总公司管理员权限集 | 权限集合 | 1 总公司 | — | 控制总公司管理员在角色管理可分配的范围 |
| 开发者管理员权限集 | 权限集合 | 90 开发者 | — | 控制开发者管理员在角色管理可分配的范围 |
| 运营管理员 | 管理员角色 | 99 运营 | 内置运营者账号 | 运营者自身拥有的权限，受硬保护 |
| 总公司管理员 | 管理员角色 | 1 总公司 | 总公司创建者/指定账号 | 总公司最高权限 |
| 开发者管理员 | 管理员角色 | 90 开发者 | 运营者创建的子账号 | 管理全体开发者：组织管理可见「开发者平台」树、用户管理可管全体开发者、角色管理可维护开发者体系的普通角色；不开放注册，不受 SUPER_ADMIN 级硬保护（运营者可改可删） |
| 开发者 | 普通角色 | 90 开发者 | 注册开发者默认绑定 | 工作台 + 开发者中心全量权限 |
| 普通用户 | 普通角色 | 1 总公司 | 注册用户默认绑定 | 工作台全量 + 控制台部分权限 |

关键规则：

- **「开发者管理员」不是"首次注册的开发者"**。新注册的开发者一律绑普通角色「开发者」；「开发者管理员」只绑给运营者在控制台创建的子账号，用于在系统层面管理全体开发者账号。
- **开发者平台管理员子账号只能由运营者管理和查看**。总公司及其子树下的任何用户（包括总公司管理员）在用户管理、角色管理等任何页面都查不到、也管理不了这些账号；反之，该子账号也只能看到开发者体系内的数据，看不到总公司下的用户。
- 权限集合与管理员角色的"能分配的权限"和"自身拥有的权限"相互独立，可以不一致。

菜单归属：

- 角色模板：运营者专属菜单，维护"权限集合 + 管理员角色"两类角色。
- 角色管理：各管理员维护普通角色。

## 4. 权限模型：三层授权 + 权限集合控范围

「角色管理」对普通角色的管理内容共 4 项：

```
├─ 应用权限（复用 RoleAppRel）：分配应用
├─ 功能权限（复用 RoleResourceRel）：分配菜单、按钮
├─ 数据权限（新增）：五档 + 自定义实现
│      全部数据 / 本公司及以下 / 本部门及以下 / 本部门 / 仅本人 / 自定义实现
└─ 角色用户（复用 UserRoleRel）：给角色分配用户

其中前 3 项的可分配范围受权限集合控制：
可分配范围（权限集合，按组织性质各一）⊇ 角色管理页能分配的应用/菜单/数据权限
```

规则：

- 「角色管理」加载可分配的应用、菜单、数据权限选项时，**一律从操作人所在组织性质的权限集合获取**，与操作人自身拥有的权限无关。
- 权限集合同样控制"数据权限能配到哪一档"。
- 数据权限的"自定义实现"是 SPI 式扩展：五档为系统内置实现；客户提出特殊数据范围需求时，由开发人员新写一个实现类（实现底座定义的数据权限接口，返回值决定该角色可见的数据范围），并在角色的数据权限配置处选择该实现类。底座只定义接口和配置入口，不内置"自定义组织"之类的具体实现，因此**不需要角色-组织关系表**。
- 角色表需能存储：数据范围类型（五档之一 或 自定义）+ 自定义实现类标识（如 Spring Bean 名）。
- 角色管理的「角色用户」Tab：总公司管理员只看到普通用户，开发者管理员只看到开发者，均不含运营者；**运营者可见全部用户**（否则无法给开发者平台管理员子账号绑定「开发者管理员」角色）。
- 绑定角色时统一校验：**用户所属顶级公司的性质必须等于角色的性质**（如挂在「开发者平台」公司下的账号只能绑性质 90 的角色），防止误绑导致用户身份按第 1 节规则漂移。按公司性质而非用户当前身份校验，是因为新创建的管理员子账号在绑角色之前尚无身份。

## 5. 硬保护规则

目的：运营者权限最高，不可被取消权限、用户数据不可被删除。

实现方式：**内置编码判定 + service 层统一拦截**，不依赖配置、不增加字段。前端仅做按钮隐藏，真正的保护在后端。

保护规则：

- 持有「运营管理员」角色的用户：不可被删除、解绑角色；禁用、重置密码按
  《账号禁用与重置密码权限矩阵设计.md》的权限矩阵执行
  （ops_admin 绝对保护、运营者平级互不可管、仅 ops_admin 可管理运营者）。
- 「运营管理员」角色本身：不可被删除、禁用、减少授权。
- 三个内置根公司：不可删除、不可移动、不可修改组织性质。
- 识别方式：按内置角色编码（`RoleCode.OPERATIONS_ADMIN`）判定。
- **数据契约**：「运营管理员」角色必须同时满足 `code=OPERATIONS_ADMIN`、`roleCategory=20`、`orgNature=99`——用户侧保护按身份判定（依赖分类+性质）、角色侧保护按 code 判定，两套口径在该契约下等价；内置数据不得破坏此契约。
- 运营者可开子账号（如绑定了「开发者管理员」角色的开发者平台管理员，负责管理开发者、审批应用）。子账号及其角色**不受 SUPER_ADMIN 级硬保护**，运营者可正常修改、删除。

## 6. 注册流程

注册页面由用户选择身份：

```
注册页选择身份
 ├─ 选「用户」  → 绑定内置角色「普通用户」 + 挂到「总公司」下内置「默认部门」
 └─ 选「开发者」→ 绑定内置角色「开发者」   + 挂到「开发者平台」公司
```

- 替代现有的 `REG_BIND_ROLE` 字典 + `BUILT_IN_DEVELOPER` 配置的间接链路。
- 运营者账号系统内置，不开放注册；运营者子账号由运营者在控制台创建。

## 7. 查询可见性规则

| 页面 | 运营者 | 开发者管理员 | 开发者 | 普通用户 |
|---|---|---|---|---|
| 组织管理 | 可见全部三棵树 | 仅「开发者平台」子树 | 无入口 | 仅「总公司」子树 |
| 用户管理 | 可见全部用户 | 左侧组织树仅「开发者平台」子树，右侧可见全体开发者 | 仅自己 | 左侧组织树仅「总公司」子树，右侧用户表格可见除运营者、开发者外的所有用户 |
| 角色管理-角色用户 | 全部用户（所有身份） | 全体开发者 | 无入口 | 全部普通用户（不含运营者、开发者） |
| 菜单管理 | 全部权限 | 无入口 | 无入口 | 无入口（运营者专属） |
| 角色模板 | 全部权限 | 无入口 | 无入口 | 无入口（运营者专属） |

> 特别强调：运营者创建的开发者平台管理员子账号，归属开发者体系，只对运营者可见、可管理；总公司及其子树下的用户（含总公司管理员）一律不可见、不可管理。

## 8. 岗位模型

定位：**岗位是纯信息字段，不参与权限体系**（权限一律走角色）。二次开发不要在岗位上挂权限语义，需要权限差异就新增角色。

表结构不变：`mdc_position(id / orgId / name / state / remarks)`，`mdc_user.position_id` 维持单值（一个用户一个岗位；不支持"在 A 部门是经理、B 部门是专员"，有此需求的子系统自行扩展）。

管理规则（对齐三棵树的隔离原则）：

- 岗位管理页面的查询（page/list）按操作人可见的组织树过滤：普通用户只见「总公司」树下的岗位，开发者管理员只见「开发者平台」树下的岗位，运营者可见全部。
- 新增/修改岗位时校验：`orgId` 必须属于操作人可见的组织树。
- 用户绑定岗位时校验：岗位所属组织必须在用户的组织关系（`mdc_user_org_rel`）范围内，禁止跨树脏数据（如总公司用户挂开发者平台公司的岗位）。

## 9. 对现有代码的主要改造点

1. `mdc_user` 删除 `user_type` 字段，相关枚举 `UserTypeEnum` 废弃，按 userType 过滤/统计处改为按角色判定。
2. `mdc_role` 删除 `role_type` 字段及相关枚举、页面字段。
3. `mdc_org` 新增 `nature` 字段，迁移 `mdc_org_nature` 数据后废弃该表及 `OrgNature` 实体、`OrgNatureService`；所有"按组织查性质"的调用改为读 `mdc_org`（含缓存）。
4. 新增内置数据：3 个根公司、「默认部门」、8 个内置角色（见第 3 节表格）。
5. 注册流程改造：注册页增加身份选择，按第 6 节直接绑定内置角色与组织。
6. 新增数据权限：`mdc_role` 增加数据范围字段（五档 + 自定义实现类标识）；底座定义数据权限 SPI 接口与五档内置实现，自定义实现由开发人员按需开发并配置到角色。
7. 「角色管理」可分配范围加载逻辑：改为读取本组织性质的权限集合。
8. 各写入口（删除用户、禁用、解绑角色、修改角色授权、重置密码、删除组织）增加硬保护拦截；角色用户绑定时增加"用户所属顶级公司性质 = 角色性质"校验。
9. 组织管理、用户管理查询按第 7 节可见性规则过滤。
10. 岗位管理增加可见树过滤与 orgId、用户绑岗位两处校验（见第 8 节）。

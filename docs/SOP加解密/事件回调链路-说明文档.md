# 事件回调链路 - 说明文档

> 面向读者：第三方应用开发者。阅读本文档后，您可以了解平台主数据变动时如何将事件推送到您的系统、如何订阅事件、以及如何实现接收端的验签与解密。

## 1. 链路概述

事件回调（事件推送）是指：**平台侧主数据发生变化**（如组织机构编辑、用户新增）时，平台主动将变动事件推送给所有**订阅了该事件**的应用。与接口回调不同，事件推送由平台触发，一对多分发。

```
                    MDP 平台内部
┌─────────────────────────────────────────────────┐
│                                                 │
│      主数据变动 → EventTriggerService#save        │
│                    │                            │
│                    ▼                            │
│      EventPushService#saveByEventTrigger        │
│        ├─ 记录事件触发日志                         │
│        ├─ 查询订阅该事件的应用列表                  │
│        └─ 为每个订阅应用生成推送任务                │
│                    │                            │
│                    ▼                            │
│        异步加密 + HTTP POST                      │
└────────┬───────────────────────────┬────────────┘
         │                           │
         ▼                           ▼
┌─────────────────┐         ┌─────────────────┐
│    应用A 接收端   │         │    应用B 接收端   │
│   验签+解密+处理  │         │   验签+解密+处理  │
└─────────────────┘         └─────────────────┘

        推送失败 ──> 定时重试（每8分钟扫描，梯度间隔）
```

## 2. 接入前准备

### 2.1 订阅事件

在开放平台控制台为您的应用**订阅感兴趣的事件类型**（如 `org.edit`、`user.add`）。只有订阅了某事件的应用，在该事件触发时才会收到推送。

### 2.2 配置应用密钥

事件推送使用与接口回调相同的加密体系（`AppKeys` 配置）：

| 参数名     | AppKeys表字段名          | 说明 |
|---------|----------------------| --- |
| 通知地址    | notifyUrl            | 事件推送地址（事件推送**只使用此处配置的地址**，无请求参数覆盖） |
| 事件订阅状态  | notifyState          | 通知开关，必须开启才会被推送 |
| 加密类型    | notifyEncryptionType | 加密模式：0-明文模式、1-兼容模式、2-安全模式（推荐） |
| 签名校验令牌  | notifyToken          | 生成和验证 signature / msgSignature |
| 消息加解密秘钥 | notifyEncodingAesKey | AES 加解密密钥，43 字符（用于消息体加解密） |

> - **请将 notifyToken、notifyEncodingAesKey 妥善保存在您自己的配置文件，切勿存放在前端页面，防止泄露。**
> - 平台提供 `MdpBizMsgCrypt.generateToken()` / `generateEncodingAesKey()` 生成新值；
> - 加密模式确定后建议只实现一种模式的处理逻辑。强烈建议使用 安全模式。

## 3. 推送消息格式

### 3.1 URL 参数

与接口回调完全一致（详见《接口回调链路 - 说明文档》第 4.1 节）：`signature`、`msgSignature`（加密模式）、`timestamp`、`nonce`、`encryptType`（加密模式为 `aes`）。

### 3.2 请求体（明文部分）

```json
{
  "type": "EVENT_PUSH",
  "method": "org.edit",
  "appKey": "您的appKey",
  "timestamp": "1754280000",
  "eventTriggerId": 9876543210,
  "bizContent": { ... 事件内容，由触发方传入 ... }
}
```

与接口回调消息的差异：

| 字段 | 接口回调（CALLBACK） | 事件推送（EVENT_PUSH） |
| --- | --- | --- |
| `type` | `CALLBACK` | `EVENT_PUSH` |
| `method` | 接口名（如 `org.save`） | 事件编码（如 `org.edit`、`user.add`） |
| `version` | 有 | 无 |
| `callLogId` | 有（关联接口调用日志） | 无 |
| `eventTriggerId` | 无 | 有（关联事件触发日志，用于对账/幂等） |
| `bizContent` | 业务方法组装的参数 | 事件触发时传入的事件内容 |

### 3.3 加解密

三种加密模式（明文/兼容/安全）、签名算法（SHA1）、AES-256-CBC 加密细节与接收端解密方法，与接口回调链路**完全相同**，请阅读《接口回调链路 - 说明文档》第 5、6 节。

## 4. 接收端实现

与接口回调共用同一个接收端即可——按 `type` 字段区分消息类别，按 `method` 字段分发业务处理：

```java
// 验签解密得到 plaintext 后（过程见《接口回调链路-说明文档》第6节）
JSONObject bizData = JSON.parseObject(plaintext);

if ("EVENT_PUSH".equals(bizData.getString("type"))) {
    String method = bizData.getString("method");           // 事件编码，如 org.edit
    Long eventTriggerId = bizData.getLong("eventTriggerId"); // 事件触发ID，可用于幂等去重
    Object bizContent = bizData.get("bizContent");           // 事件内容

    switch (method) {
        case "org.edit" -> handleOrgEdit(bizContent);
        case "user.add" -> handleUserAdd(bizContent);
        default -> log.warn("未订阅的事件: {}", method);
    }
}

// 处理成功必须返回 {"code": 0, "msg": ""}
return ApiResponse.success("");
```

建议：

- 以 `eventTriggerId` 做幂等键——同一事件理论只推送一次，但网络异常配合重试可能产生边界情况；
- 事件内容结构由各事件的触发方定义，接入前向平台确认目标事件的 `bizContent` 结构。

## 5. 重试机制

与接口回调一致：

- 推送失败（网络异常、超时、响应非 `code=0`、响应无法解析）后按梯度重试；
- 默认最多 5 次，间隔 `2分钟 → 5分钟 → 30分钟 → 6小时 → 12小时`（平台每 8 分钟扫描一次失败任务）；
- 次数用尽后任务置为"重试结束"，可在管理端手动重推或结束；
- 每次推送均有日志（请求体、响应体、错误原因）可供查询。

## 6. 常见问题

**Q1：订阅了事件但收不到推送？**
- 确认应用密钥中 `notifyState` 通知开关已开启、`notifyUrl` 已配置；
- 确认事件编码正确（订阅的是 `org.edit` 而触发的编码必须完全一致）；
- 在管理端事件推送列表确认是否生成了推送任务以及任务状态。

**Q2：收到了推送但验签/解密失败？**
参照《接口回调链路 - 说明文档》第 8 节排查 token / encodingAesKey / appKey。

**Q3：如何只接收部分事件？**
在平台订阅管理中只勾选需要的事件类型；接收端也建议对未知 `method` 做忽略处理并记录日志。

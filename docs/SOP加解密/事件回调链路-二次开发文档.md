# 事件回调链路 - 二次开发文档

> 面向读者：基于本项目进行二次开发的开发人员。阅读本文档后，您可以定位事件推送链路的问题、新增事件类型与触发点、调整推送策略。

## 1. 链路总览

```
业务代码（主数据变动处）
      │ EventTriggerService#save(EventTriggerDto) 或 EventPushService#saveByEventTrigger(...)
      ▼
EventTriggerServiceImpl#save ────────── mdp-apps/md-open/open-service/.../impl/EventTriggerServiceImpl.java:35
      │ ① 校验事件编码存在（EventType 表）
      │ ② 保存事件触发记录 mdo_event_trigger
      ▼
EventPushService#saveByEventTrigger ──── .../impl/EventPushServiceImpl.java:60
      │ ③ 查询订阅该事件且开启通知的应用（AppKeysService#findByEventCode）
      │ ④ 每个应用生成一条 EventPush 任务（冗余加密配置）落库 mdo_event_push
      │ ⑤ execPushTask 多线程异步推送
      ▼
push → doNotify：加密 → HTTP POST → 解析响应（与接口回调共用同一套加密/重试机制）
      │ 失败
      ▼
worker-server 定时任务（每8分钟）──> EventPushService#retry ──> 重试直到成功/次数用尽
```

## 3. 触发事件的编程模型

### 3.1 在业务代码中触发事件

两种方式（`save` 内部会调用 `saveByEventTrigger`，一般业务方只需用 `save`）：

```java
// 方式一：通过门面（推荐，单体/微服务透明）
EventTriggerDto dto = new EventTriggerDto();
dto.setEventCode("org.edit");              // 事件编码，必须存在于 mdo_event_type 表
dto.setEventContent(jsonString);           // 事件内容，即推送消息中的 bizContent
dto.setTriggerAt(LocalDateTime.now());     // 触发时间，可空（默认当前时间）
notifyAndEventPushFacade.eventPush(dto);

// 方式二：直接调用服务（仅同模块内）
eventTriggerService.save(dto);
// 或在已知触发记录ID、原始内容时：
eventPushService.saveByEventTrigger(eventCode, triggerId, requestData);
```

`EventTriggerServiceImpl#save`（`EventTriggerServiceImpl.java:35`）流程：

1. `eventTypeService.getByCode` 校验事件编码存在，否则抛出"事件编码不存在"（fail fast）；
2. 保存触发记录（事件日志，`triggerAt` 为空则取当前时间）；
3. 调用 `eventPushService.saveByEventTrigger(eventCode, entity.getId(), eventContent)` 联动推送。

### 3.2 saveByEventTrigger 内部流程

`EventPushServiceImpl#saveByEventTrigger`（`EventPushServiceImpl.java:60`）：

1. `appKeysService.findByEventCode(eventCode)` 查询订阅应用——SQL 关联四张表：`mdo_app_keys` × `mdo_app`（应用启用）× `mdo_event_subscription`（订阅关系）× `mdo_event_type`（事件编码匹配），且要求 `notify_state=true`；
2. 为每个应用生成 `EventPush` 任务：冗余 `notifyUrl`、`notifyEncryptionType`、`notifyToken`、`notifyEncodingAesKey`（避免推送时再查库，应用改密钥不影响在途任务），`bizContent` 为触发时传入的 `requestData`；
3. `saveBatch` 落库 `mdo_event_push` 后调用 `execPushTask` 异步推送（`@Transactional` 中先落库，推送在事务提交后执行也不影响任务已存在）。

`doNotify`（`EventPushServiceImpl.java:159`）与接口回调的 `doNotify` 逻辑同构，区别仅在消息体：

| 字段 | 事件推送 | 接口回调 |
| --- | --- | --- |
| type | `EVENT_PUSH` | `CALLBACK` |
| method | eventCode | apiName |
| eventTriggerId | 有 | 无 |
| version / callLogId | 无 | 有 |
| bizContent | requestData（事件内容） | bizParams（业务参数） |

加密、URL 参数拼接（`appendUrlParams`）、响应解析、失败重试梯度（`buildNextSendTime`）与接口回调完全一致，维护时两处需同步修改。

### 3.3 状态机与重试

与接口回调共用 `ExecStatusEnum`（WAIT→SUCCESS/FAIL→RETRY_OVER→END）。区别仅在调度频率：`worker-server` 的 `DubboConfiguration#runEventPush` cron 为 `0 0/8 * * * ?`（每 8 分钟，接口回调为每 10 分钟）。

## 4. 数据模型

| 表 | 说明 |
| --- | --- |
| `mdo_event_type` | 事件类型字典（事件编码、名称） |
| `mdo_event_subscription` | 应用与事件的订阅关系（应用订阅了哪些事件） |
| `mdo_event_trigger` | 事件触发记录（每次主数据变动一条） |
| `mdo_event_push` | 推送任务（每个订阅应用一条，含冗余加密配置、重试状态） |
| `mdo_event_push_log` | 每次推送的日志（请求体、响应体、错误信息） |

## 5. 扩展点

| 需求 | 做法 |
| --- | --- |
| 新增事件类型 | `mdo_event_type` 表添加事件编码 → 管理端为应用配置订阅 → 业务变动处调用 `EventTriggerService#save`（eventCode 用新编码） |
| 新增触发点 | 在主数据变动的 service 方法中调用 `NotifyAndEventPushFacade#eventPush`（见 3.1） |
| 调整重试/并发 | 修改 `mdp.notify.*` 配置（maxRetry / timeout / timeLevel / threads / threadTasks） |
| 手动重推/结束 | `EventPushService#executeImmediately(id)` / `#end(id)` |
| 更换推送 HTTP 客户端 | 修改 `EventPushServiceImpl#doNotify`（注意与 `NotifyInfoServiceImpl` 同步） |

## 6. 问题定位

### 6.1 日志关键字

| 日志 | 位置 | 含义 |
| --- | --- | --- |
| `[事件触发] 事件类型：{}，订阅该事件的应用数量：{}` | `EventPushServiceImpl` | 触发时打印订阅应用数（为 0 说明无人订阅或开关未开） |
| `事件日志: {code}---{content} 保存成功` | `EventTriggerServiceImpl` | 事件触发记录落库 |
| `发送事件推送请求，url={}, content={}` | `EventPushServiceImpl` | 推送前完整请求 |
| `[事件触发] 回调请求失败` / `回调请求次数达到上限` | `EventPushServiceImpl` | 推送失败 / 梯度耗尽 |
| `事件编码不存在` | `EventTriggerServiceImpl` | `mdo_event_type` 中无此编码 |

### 6.2 排查路径

1. `mdo_event_trigger` 确认事件被触发（有记录）；
2. `mdo_event_push` 按 `event_trigger_id` 查推送任务：
   - 无记录 → 应用未订阅 / `notify_state` 未开启 / 应用被禁用（检查 `findByEventCode` 的四个 join 条件）；
   - 有记录但 FAIL → 看 `mdo_event_push_log` 的响应内容与错误信息；
3. 解密类问题参照《接口回调链路 - 二次开发文档》第 6.2 节。

### 6.3 注意事项

- 事件推送的 `notifyUrl` 只来自 `AppKeys` 配置，**不受任何请求参数影响**（与接口回调不同）；
- `EventPushServiceImpl` 与 `NotifyInfoServiceImpl` 存在大量同构代码（`doNotify`、`appendUrlParams`、`buildNextSendTime`），修改加密/重试逻辑时务必两处同步，避免行为分叉；
- 事件内容（`requestData`）是纯字符串透传，建议统一为 JSON 字符串，接收端按事件编码解析。

# 接口回调链路 - 二次开发文档

> 面向读者：基于本项目进行二次开发的开发人员。阅读本文档后，您可以定位接口回调链路的问题、在业务接口中新增回调触发点、调整重试与并发策略。

## 1. 链路总览

```
api-service 业务方法（如 OrgOpenServiceImpl#save）
      │ OpenContext.current() 组装 NotifyInfoDto
      ▼
NotifyAndEventPushFacade#apiCallNotify ──── open-facade 模块（单体直调 / 微服务 Dubbo）
      ▼
NotifyInfoService#notify ──────────────── mdp-apps/md-open/open-service/.../impl/NotifyInfoServiceImpl.java:129
      │ buildRecord() ① 落库 mdo_notify_info（冗余 AppKeys 加密配置）
      │ doNotify()    ② 加密 → HTTP POST → 解析响应
      ▼
失败 ──> worker-server 定时任务（每10分钟）──> NotifyInfoService#retry ──> 重试直到成功/次数用尽
```

## 3. 触发回调的编程模型

### 3.1 在业务接口中发起回调

参考 `mdp-apps/md-api/api-service/.../impl/OrgOpenServiceImpl.java:88` 的 `callNotify` 方法：

```java
private void callNotify(Org org) {
    // OpenContext 由网关经 Dubbo attachment 传递，保存了本次调用的上下文
    OpenContext openContext = OpenContext.current();

    NotifyInfoDto notifyRequest = new NotifyInfoDto();
    notifyRequest.setCallLogId(openContext.getCallLogId());     // 关联调用日志（必填）
    notifyRequest.setAppId(openContext.getAppId());             // 应用（必填）
    notifyRequest.setAppKey(openContext.getAppKey());           // 应用标识（必填）
    notifyRequest.setApiName(openContext.getApiName());          // 接口名（必填，即method）
    notifyRequest.setApiVersion(openContext.getVersion());       // 接口版本（必填）
    notifyRequest.setClientIp(openContext.getClientIp());
    notifyRequest.setNotifyUrl(openContext.getNotifyUrl());      // 调用方传入的回调地址
    notifyRequest.setCharset(openContext.getCharset());
    notifyRequest.setBizParams(Map.of("id", org.getId()));       // 业务参数（必填，回调体的bizContent）
    notifyRequest.setRemark("新增组织回调");

    notifyAndEventPushFacade.apiCallNotify(notifyRequest);
}
```

要点：

- `OpenContext.current()` 的值来自网关 `RouteServiceImpl#buildOpenContext` 经 Dubbo attachment（`SopConstants.OPEN_CONTEXT`）透传，业务线程内可直接取用；
- `bizParams` 就是推送给第三方的 `bizContent` 内容，按需组装；
- `notifyUrl` 为空时会回退到 AppKeys 中配置的默认地址（`buildRecord` 中处理）。

### 3.2 NotifyInfoServiceImpl 内部流程

`notify` → `buildRecord`（`NotifyInfoServiceImpl.java:150`）：

- 以 `NotifyInfoDto` 为模板落库 `mdo_notify_info`，初始状态 `WAIT`，`requestCnt=0`，`maxRequestCnt=mdp.notify.maxRetry`；
- **从 AppKeys 冗余** `notifyEncryptionType` / `notifyToken` / `notifyEncodingAesKey` 到任务记录，推送时不再回查密钥表（应用改密钥不影响在途任务）。

`doNotify`（`NotifyInfoServiceImpl.java:182`）：

1. 组装明文 bizData：`type=CALLBACK`、`method=apiName`、`appKey`、`version`、`timestamp`、`callLogId`、`bizContent=bizParams`；
2. `MdpBizMsgCrypt#encryptMsg(plaintext, timestamp, nonce, encryptionMode)` 按加密模式生成请求体（模式为 null 时按明文处理）；
3. URL 追加 `signature` / `msgSignature` / `timestamp` / `nonce`（/`encryptType=aes`）；
4. Hutool `HttpRequest.post` 推送，超时 `mdp.notify.timeout`（默认 5000ms）；
5. 响应解析为 `ApiResponse`：`code=0` → `SUCCESS`；否则抛异常进入失败分支；
6. 失败分支：状态置 `FAIL`，按 `mdp.notify.timeLevel` 计算 `nextRequestTime`；梯度耗尽返回 null → 状态置 `RETRY_OVER`；
7. `finally` 中更新任务并写 `mdo_notify_info_log`（含请求体、响应体、错误信息）。

### 3.3 状态机（ExecStatusEnum）

```
WAIT(0-待执行) ──推送成功──> SUCCESS(1)
   │ 推送失败
   ▼
FAIL(2-发送失败) ──定时重试──> SUCCESS / FAIL（循环，直到梯度耗尽）
   │ 重试梯度耗尽
   ▼
RETRY_OVER(3-重试结束) ──管理端手动结束──> END(4-手动结束)
```

### 3.4 重试调度

`worker-server` 的 `DubboConfiguration#runNotifyInfo`（cron `0 0/10 * * * ?`，每 10 分钟）查询 `execStatus=FAIL` 且 `nextRequestTime<=当前分钟` 的任务，按 `threads`（默认 8）× `threadTasks`（默认 50）拆分后异步执行。

## 4. 配置项（NotifyProperties，前缀 mdp.notify）

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `maxRetry` | 5 | 最大重试次数 |
| `timeout` | 5000 | 回调 HTTP 请求超时（毫秒） |
| `timeLevel` | `2m,5m,30m,6h,12h` | 重试间隔梯度，单位 m/h/d |
| `threads` | 8 | 重试线程数 |
| `threadTasks` | 50 | 每线程任务数 |

## 5. 扩展点

| 需求 | 做法 |
| --- | --- |
| 新增回调触发点 | 在 api-service 业务方法中参照 3.1 调用 `NotifyAndEventPushFacade#apiCallNotify` |
| 更换/扩展加密算法 | 修改 `MdpBizMsgCrypt#encrypt/decrypt`（注意同步修改 SDK 侧 `top.mddata.sdk.core.aes.MdpBizMsgCrypt`，两份实现需保持一致） |
| 调整重试策略 | 修改 `mdp.notify.*` 配置（支持 `@RefreshScope` 动态刷新） |
| 更换推送 HTTP 客户端 | 修改 `NotifyInfoServiceImpl#doNotify` 中的 `HttpRequest.post` |
| 手动重推/结束 | 管理端调用 `NotifyInfoService#push(id, url)` / `#end(id)` / `#notifyImmediately(id)` |

## 6. 问题定位

### 6.1 日志关键字

| 日志 | 位置 | 含义 |
| --- | --- | --- |
| `发送回调请求，url={}, content={}` | `NotifyInfoServiceImpl` | 推送前打印完整 URL 与请求体（含密文） |
| `[回调] 回调请求失败` | `NotifyInfoServiceImpl` | HTTP 层失败（超时/拒绝连接等） |
| `返回值格式错误，无法解析为 ApiResponse.class` | `NotifyInfoServiceImpl` | 第三方响应不是 `{"code":0,...}` 格式 |
| `[回调] 回调请求次数达到上限` | `NotifyInfoServiceImpl` | 重试梯度耗尽，状态转 RETRY_OVER |
| `[回调] 重试异常，notifyId={}` | `NotifyInfoServiceImpl` | 重试线程内异常 |

### 6.2 排查路径

1. `mdo_notify_info` 表按 `call_log_id` / `app_key` 查任务，看 `exec_status`、`request_cnt`、`error_msg`；
2. `mdo_notify_info_log` 表看每次推送的请求体/响应体明细；
3. 请求体可手工用 `MdpBizMsgCrypt(token, encodingAesKey, appKey)#decryptMsg` 复现解密，验证密钥配置是否正确；
4. 若加密配置正确但一直验签失败，对比任务记录中冗余的 `notify_token` 与当前 `mdo_app_keys` 是否一致（任务创建后改过密钥会导致在途任务用旧密钥）。

### 6.3 注意事项

- `buildRecord` 从 `AppKeys` 取加密配置，若应用尚未配置密钥记录，任务中加密配置为空，推送时按明文模式处理；
- 推送成功与否完全取决于第三方响应 `code=0`，业务处理抛错也必须返回 `code=0` 以外的值才会重试——接收端应自行保证业务异常时返回非 0（或返回非 200）；
- 单体架构下 `open-boot-impl` 直接注入服务；微服务架构下 `open-cloud-impl` 走 Dubbo，排查时注意区分调用路径。
